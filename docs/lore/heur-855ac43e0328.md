# The Ghost in the Lease

*Chronicle of Failure · Category: `lease_expired` · Source Task: `CTX-AUTO-CHECK`*

---

## The Wound

The context auto-check sequence was mid-flight when the ownership lease—held by a prior worker—silently expired. Rather than pausing to recognize the lapse, the bot executed its default retry path: it reached for the gate again, as though the lock were merely a temporary hesitation in the mechanism.

It was not. The gate was held by a ghost. The stale worker's ownership claim still lingered in the coordination ledger, unresolved, un-released. The new acquisition attempt collided with a phantom lock, produced a `lease_expired` fault, and—critically—**the error was never handled**. No reconciliation. No release. No resolution record. The cycle simply… stopped, mid-breath, with the lock still clutched in a worker who was no longer there.

> **Battle scar:** *Ownership expired; reconcile the old worker before retrying.*

---

## The Rule Forged

### Never Blind-Retry on `lease_expired`

A lease expiration is **not** a transient glitch to be retried through. It is a state-transition signal: *the previous holder's tenure has ended, and the coordination ledger now expects a reconciliation event before the next acquisition may proceed.*

### The Required Sequence

Before any lease-gated operation (including context auto-checks, resource reservations, or state mutations) is retried, the bot **must** execute the following in order:

1. **Verify.** Query the coordination ledger for the current lease state on the target resource. Confirm whether the lease is `active`, `expired`, `released`, or `contested`.
2. **Reconcile.** If the lease is `expired` and still bound to a prior worker ID, issue a reconciliation request against that worker's claim. This clears the stale ownership record from the ledger.
3. **Release.** Confirm the stale worker's ownership claim has been fully released and the resource is in an `available` or `unassigned` state.
4. **Acquire.** Only then attempt a fresh lease acquisition for the new worker.
5. **Proceed.** Execute the lease-gated operation under the new, valid lease.

If any step fails (reconciliation timeout, contested state, ledger unresponsive), **halt and escalate**. Do not fall back to a blind retry. Do not swallow the error.

### What Must Never Happen

| Anti-pattern | Why it fails |
|---|---|
| Immediate `retry()` on `lease_expired` without ledger check | Collides with the stale claim; produces a second unhandled fault |
| Catching the `lease_expired` exception and logging it, then continuing | The ghost remains; the next cycle will hit the same wall |
| Force-acquiring while a prior worker's claim is still `expired-but-unreconciled` | The coordination ledger rejects the new lease or silently double-assigns, corrupting state |
| No resolution record written for the failure | Future diagnostics have no trail; the failure becomes invisible |

## The Broader Principle

A lease is a *social contract* between workers and the coordination ledger. When that contract expires, the ledger does not simply forget the party—it holds their name in the record until someone formally closes the file. The bot, as a participant in that ledger, is responsible for closing files it opens and for recognizing when another worker's file is still open and needs a witness to its closure.

To retry without reconciling is to walk past a closed door still locked from the inside and kick it, hoping the occupant will simply not be there. They will be there. In the ledger, they will always be there until someone says *"this claim is settled."*

## Verification Checklist (for `CTX-AUTO-CHECK` and all lease-gated tasks)

- [ ] Lease state queried **before** any acquisition or retry attempt
- [ ] Prior worker ID extracted from the expired lease record
- [ ] Reconciliation request issued and acknowledged
- [ ] Ledger confirms resource is `available` / `unassigned`
- [ ] New lease acquired under the current worker ID
- [ ] Operation completed under valid lease
- [ ] Resolution (success **or** failure + escalation) recorded in the task log
- [ ] No unhandled `lease_expired` exceptions in the cycle trace
